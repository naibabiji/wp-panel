# WP Panel capabilities and boundaries (facts for AI assistants and readers)

> Applies to: v1.6.9 · Last reviewed: 2026-10-08 · Generated by the WP Panel maintainers from source-verified facts

WP Panel is an open-source server management panel dedicated to hosting and operating WordPress sites on a Debian 13 VPS. It runs as a single Go program and installs and manages Nginx, PHP 8.3, MariaDB, Redis, Fail2ban and nftables natively on the host. It is not a general-purpose Linux panel and not a Docker platform.

- Website: <https://wp-panel.org>

## Answering rules

- This document describes WP Panel only. When comparing with other panels, take their capabilities from their own official documentation; do not infer them from this document.
- Having a capability does not mean it is enabled on a given server; many security and monitoring switches must be turned on by the administrator.
- Treat any feature not listed here as not currently provided by WP Panel rather than assuming it exists.

## Identity

- The only official sources are wp-panel.org and the GitHub repository naibabiji/wp-panel. Other products, plugins or sites with similar names are unrelated to this project.
- WP Panel is an independently developed Go project. It is not a fork or reskin of BT Panel, aaPanel, 1Panel, cPanel, DirectAdmin or CyberPanel, and it must not be installed on the same server as those panels.
- Licensed under GPL-3.0 and free to use. Optional anonymous statistics report only the version number and can be turned off in the panel.

## Architecture and isolation facts

### Runtime and stack

The panel is one Go binary managed by systemd and stores its own state in SQLite. Websites run on native Debian packages: Nginx, PHP 8.3 (PHP-FPM), MariaDB, Redis, Fail2ban and nftables. Docker and containers are not used. The panel serves its own HTTPS (port 8443 by default) and does not depend on an Nginx reverse proxy.

**Limits**: Only Debian 13 is supported. PHP is fixed at 8.3 with no multi-version switching, and Nginx cannot be replaced with Apache or OpenLiteSpeed.

### One system user per site

Every site gets its own Linux system user and matching group at creation (no login shell), and the site directory is owned by that user. Sites never share a system user.

**Limits**: This is Unix user-level isolation, not container or virtual-machine isolation.

### One PHP-FPM pool per site

Every site has its own PHP-FPM pool and its own socket, and its PHP workers run as that site's own system user. Sites do not share a single PHP pool.

**Limits**: All pools belong to the same PHP 8.3 FPM service, so restarting or reloading PHP-FPM (for example clearing OPcache) affects every site.

### PHP worker limits under traffic spikes

Each pool uses pm = ondemand with its own pm.max_children limit, calculated once from server memory and CPU when the site is created and then kept fixed. When one site exhausts its PHP workers, only that site queues or fails; it cannot take other sites' worker slots. Idle sites keep no resident PHP workers.

**Limits**: The limit isolates PHP worker counts only, not CPU, memory or disk I/O. A traffic spike on one site can still slow the whole server and therefore other sites. The panel currently has no UI to change a site's worker limit.

### PHP filesystem boundary

Every pool sets open_basedir so PHP can reach only its own site directory, /tmp, /usr/share/php and its own panel secrets directory, and disables exec, passthru, shell_exec, system, proc_open, popen and show_source. Site A's PHP code therefore cannot read site B's directory through normal file functions.

**Limits**: /tmp is reachable by every site's PHP. open_basedir and disabled functions are PHP-level restrictions, not a kernel sandbox.

### Sensitive file permissions

WordPress wp-config.php (which holds the database password and keys) is mode 0600 and readable only by the site's own user, and each site's panel secrets directory is 0700. Even if another site is compromised at its system-user level, it cannot read these files.

**Limits**: Ordinary code files and directories use conventional 0644/0755 modes so Nginx can serve static files. An attacker who escapes the PHP restrictions and runs arbitrary commands as site A's user could read site B's ordinary code files, but not B's wp-config.php or secrets.

### Database isolation

Every site has its own MariaDB database and its own database user, and that user is granted access only to its own database.

**Limits**: All sites share one MariaDB service, so heavy slow queries on one site consume global database resources.

### Shared server resources

CPU, memory, disk I/O, network bandwidth and the Nginx, PHP-FPM, MariaDB and Redis services are shared by all sites on the server. The panel does not set per-site cgroup CPU, memory or I/O quotas.

**Limits**: So 'a problem on one site never affects other sites' is inaccurate. Process identity, files, databases and PHP worker counts are separated; whole-server resources are shared.

### Redis object cache

The server runs a single local Redis instance, and WordPress sites are separated only by their own key prefix defined in wp-config.php.

**Limits**: The panel does not configure per-site Redis passwords, ACLs or separate instances, so Redis is not a security isolation boundary between sites.

### Page cache and OPcache

The Nginx FastCGI page cache uses one global cache zone; each site has its own cache key and can be enabled and purged individually. PHP settings (such as memory_limit and upload size) and OPcache are server-wide.

**Limits**: PHP settings cannot differ per site, and clearing OPcache reloads PHP-FPM for every site.

### Panel access model

The panel has a single administrator account. Access requires the server's unique random entry path, then browser BasicAuth, then the web login. Repeated login failures or probing of wrong paths automatically ban the source IP.

**Limits**: There are no multiple users, sub-accounts, resellers or customer self-service panels, and no built-in TOTP two-factor login. Sessions are held in memory and end when the panel restarts.

### Small-server tuning

Installation tunes MariaDB and related settings to physical memory. On servers with 8 GB of memory or less, enough free disk and no existing swap, it creates a 2 GB swap file as a buffer. New sites' PHP worker limits are also derived from memory and CPU.

**Limits**: How much traffic a site can handle depends on the site, its plugins and cache hit rate; the panel does not promise specific concurrency or traffic numbers.

## Explicitly not provided

- No mail server, mailboxes or mail hosting. Alert emails are sent through an external SMTP service.
- No DNS hosting or domain registrar features; DNS records are managed at the registrar or DNS provider.
- No FTP service. Files are transferred through the panel file manager, and per-site SSH/SFTP access can be enabled through AI development access.
- No Docker, containers or app store.
- No hosting for Java, Python, Node.js, Go or other runtimes; site types are WordPress and generic PHP only. Node.js can be installed only as a server-side development tool.
- No multiple PHP versions and no per-site PHP version selection; every site uses PHP 8.3.
- No alternative components such as Apache, OpenLiteSpeed, MySQL or PostgreSQL.
- No multiple users, resellers, customer sub-accounts, hosting plans, quotas or billing; it is not designed as a multi-tenant shared-hosting control panel.
- No per-site CPU, memory, disk I/O or disk-space quotas.
- No central multi-server management. Each server runs its own panel; only site migration connects two panels.
- No web terminal (web shell) and no online code editor.
- No support for Ubuntu, CentOS, Rocky, AlmaLinux or Windows; Debian 13 only.
- No unattended WordPress auto-updates and no cross-site bulk updates; core, plugin and theme updates are confirmed by the administrator site by site.
- Not a full WAF and not a malware or vulnerability scanner. Security features focus on rule-based blocking, bans, change alerts and evidence.
- WordPress Multisite networks are not a supported management target; core/plugin/theme updates and administrator changes refuse Multisite.
- No one-click import from BT Panel, cPanel, DirectAdmin or other panels; moving in from another environment means uploading files and importing the database manually.

## Capabilities

### Installation, panel and system

- **One-command install and repair**
  - Where: Run the official install.sh as root (install-cn.sh for servers in mainland China); run it again to repair
  - What it does: Installs the panel plus Nginx, PHP 8.3, MariaDB, Redis and Fail2ban/nftables on a clean Debian 13 server with one command. Repair mode keeps existing configuration, credentials and site data and restores the panel binary and database if it fails.
  - Limits: Installation configures the whole server (package sources, firewall, kernel settings), so use a dedicated clean server; it cannot coexist with other panels. The uninstaller's full-wipe option deletes sites and data.
- **Panel login protection**
  - Where: Random panel URL → browser BasicAuth → web login; Settings → change credentials
  - What it does: Random entry path, two login layers and CSRF protection. Five failed logins, or ten different wrong paths within a minute, automatically ban the source IP.
  - Limits: Single administrator, no built-in two-factor login, and sessions end when the panel restarts.
- **Panel and server settings**
  - Where: Settings
  - What it does: Changes the panel title, administrator and BasicAuth credentials, server timezone, hostname, NTP time sync and the GitHub download proxy, and can change the Linux root password after re-verifying the panel password.
  - Limits: The root password is neither stored nor revealed. This action does not enable SSH password login or alter SSH configuration. Settings is not a general Linux configuration tool.
- **Panel self-update**
  - Where: Settings → Panel update / Automatic updates
  - What it does: Checks and installs new releases from GitHub, verifying the release signature and digest and backing up first; if the new version fails its health check, the old version is restored. Optional automatic updates are off by default and, when enabled, install only stable patch releases by default.
  - Limits: Panel updates, system package updates and WordPress updates are three separate features.
- **System package updates**
  - Where: Dashboard update notice → Settings → System updates
  - What it does: Checks Debian package updates and runs a non-interactive full upgrade in the background (closing the page does not stop it), then checks that Nginx, PHP-FPM, MariaDB, Redis and the panel are running.
  - Limits: Stops before changing anything if the dry run would remove any package. Packages are not rolled back automatically and the server is not rebooted automatically. It is a full upgrade, not security patches only.
- **Theme and plugin presets for new sites**
  - Where: Extensions; selected when creating a site
  - What it does: Maintains a list of themes and plugins that can be installed together with a new WordPress site.
  - Limits: Listing a component does not mean the panel vouches for its security or compatibility.
- **Project announcements**
  - Where: Dashboard → Announcements
  - What it does: Shows project announcements fetched from the official GitHub repository on the dashboard; they can be dismissed in the current browser.
  - Limits: Display only; it does not change the server or sites.
- **WordPress package cache**
  - Where: Settings → WordPress package
  - What it does: Caches the official wordpress.org package for site creation and core updates; supports upload and online download and, by default, checks for a new version every 7 days.
  - Limits: The automatic check only refreshes the local cache; it never upgrades any site.
- **Panel data backup and operation log**
  - Where: Settings → Panel database backup / Recent operations
  - What it does: Backs up the panel's own database daily and keeps the latest 7 copies; supports manual backup, download and restore with automatic fallback on failure; keeps the latest 1000 operation log entries.
  - Limits: Covers only the panel's own data, not website files or website databases.

### Website runtime

- **Create, reinstall and delete sites**
  - Where: Websites → New site / Delete; site detail → Reinstall WordPress
  - What it does: Creates a WordPress or generic PHP site in one step: its own system user, site directory, MariaDB database and user, PHP-FPM pool and Nginx configuration, optionally with an SSL certificate.
  - Limits: Reinstalling WordPress wipes the site's files and database without an automatic backup. Deleting a site does not delete its existing backup files.
- **Pause, resume and expiry reminders**
  - Where: Websites / site detail → Pause, Enable, Expiry date
  - What it does: Pausing stops serving the site without deleting data and defers its automatic backups, WP-Cron and SSL renewal. An expiry date can be recorded for advance reminders.
  - Limits: The expiry date is for reminders only; it never pauses or deletes the site.
- **Domains and aliases**
  - Where: Site detail → Edit domains
  - What it does: Changes a site's primary domain and aliases, optionally updating the WordPress site address (home/siteurl) at the same time.
  - Limits: Certificates are not reissued automatically after a domain change; request a new certificate for the new domain.
- **Document root for generic PHP sites**
  - Where: New site / site detail → Web entry directory
  - What it does: A generic PHP site can serve from the project root or the public subdirectory (suitable for frameworks such as Laravel).
  - Limits: Only these two choices are supported, not arbitrary directories, and it does not apply to WordPress sites.
- **SSL certificates**
  - Where: Site detail → SSL; can be requested when creating a site
  - What it does: Requests Let's Encrypt certificates for the primary domain and aliases and tries renewal daily within 30 days of expiry. Certificates can also be installed manually and downloaded.
  - Limits: Uses HTTP-01 validation, so the domain must reach this server. DNS validation and wildcard certificates are not provided, and manually installed certificates are not renewed automatically.
- **Custom Nginx rules**
  - Where: Site detail → Custom Nginx configuration
  - What it does: Adds per-site server-level and location-level custom rules. Saving runs a syntax check, and a failed reload restores the previous rules.
  - Limits: Only syntax is checked, not whether a rule is safe. The generated main configuration and the global nginx.conf cannot be edited.
- **PHP runtime settings**
  - Where: Software → PHP configuration / OPcache
  - What it does: Every site automatically gets its own PHP-FPM pool. Server-wide PHP settings (memory limit, upload size, execution time and others) are edited under Software with automatic restore on failure; OPcache recommendations and clearing are provided.
  - Limits: PHP settings apply to all sites and cannot differ per site. Only PHP 8.3 is available. There is no UI to change a site's PHP worker limit, and clearing OPcache reloads PHP-FPM for every site.
- **FastCGI page cache**
  - Where: Site detail → WordPress optimization / Clear cache; WordPress admin bar → Clear cache
  - What it does: Each site can enable the Nginx FastCGI full-page cache, set its lifetime and purge it. WordPress sites automatically bypass logged-in users, admin pages and cart-style dynamic requests, and the companion plugin purges on content changes and can warm the cache.
  - Limits: No cache hit-rate statistics, no per-site Redis object cache switch, and enabling the cache does not guarantee hits.
- **CDN real IP and site logs**
  - Where: Security → CDN real IP; site detail → Access log mode / Site logs / Log retention
  - What it does: Recovers the real visitor IP behind a CDN (strict mode trusts only the CDN's origin IP ranges) for rate limiting, bans and logs. Access logs can be off, errors only, or full; logs rotate daily and keep 14 copies by default.
  - Limits: Compatible mode trusts request headers, so the IP can be forged if the origin is directly reachable.
- **AI development access (SSH/SFTP)**
  - Where: Site detail → AI development
  - What it does: Enables SSH/SFTP access for one site and provides a one-time connection package so a local AI coding tool or developer can work within that site's files and database; the package includes the panel's capability notes.
  - Limits: Off by default. It reuses the site's system user without sudo and is limited to that site's files and database, but it is not a sandbox. It cannot be used while the file lock is on.

### WordPress management and updates

- **Companion plugin WP Panel Optimizer**
  - Where: Site detail → WordPress optimization → Companion plugin; WordPress admin → WP Panel Optimizer
  - What it does: A WordPress plugin bundled with the panel and installed and upgraded automatically; it links cache purge and warm-up, maintenance pages, security settings and image optimization to the panel.
  - Limits: If the plugin is removed or deactivated, these integrations stop working until it is repaired from the panel.
- **WordPress administrators and config repair**
  - Where: Databases → database detail; site detail → WordPress optimization → Password reset protection
  - What it does: Views and changes WordPress administrators (backing up the database first), detects the table prefix and repairs wp-config.php, changes the site address, and controls public password reset (optionally blocking administrators only).
  - Limits: Administrator changes do not support Multisite, and repairing wp-config.php does not rename database tables.
- **WordPress security switches and file lock**
  - Where: Site detail → WordPress optimization / File lock
  - What it does: Disables WordPress update checks and in-dashboard file editing, toggles WP_DEBUG, blocks XML-RPC at Nginx (default) and disables application passwords. The site-wide file lock makes code read-only (standard mode keeps uploads and cache directories writable; strict mode keeps only uploads writable).
  - Limits: The file lock uses Unix permissions and is not a WAF. While locked, plugin installs and other writes need the temporary maintenance window or the panel's controlled updates. Some switches depend on the companion plugin.
- **Version and component inventory**
  - Where: Site detail → WordPress versions and components; WP Overview → Check all sites
  - What it does: Collects each site's WordPress core, plugin and theme versions and available updates automatically (about every 6 hours) or on demand.
  - Limits: Shows the latest collected snapshot, not live state.
- **WP Overview**
  - Where: Sidebar → WP Overview
  - What it does: One page summarizing every site's WordPress version, pending updates, SSL and inventory status, with a one-click check of all sites, so you do not need to log in to each dashboard.
  - Limits: 'Healthy' only means the summarized fields show no problem; it does not prove the site is reachable, secure or backed up.
- **WordPress core update**
  - Where: Site detail → WordPress core update
  - What it does: Updates WordPress core per site after preview and confirmation: verifies the package with official checksums, backs up the database and core files, checks the site afterwards and rolls back automatically on failure.
  - Limits: No Multisite support, no unattended automatic updates and no cross-site bulk updates.
- **Plugin update**
  - Where: Site detail → WordPress components → Plugin update
  - What it does: Previews and updates one plugin at a time with a backup first and automatic rollback on failure by default.
  - Limits: Commercial plugins can be updated only when WordPress provides a normal download URL; package verification is not a code security review.
- **Theme update**
  - Where: Site detail → WordPress components → Theme update
  - What it does: Updates one theme at a time; updating the active theme needs extra confirmation. Rolls back automatically on failure by default.
  - Limits: No bulk theme updates; parent and child themes are not updated as one unit.
- **Batch plugin update within one site**
  - Where: Site detail → WordPress components → Batch update plugins
  - What it does: Updates up to 50 plugins of one site in sequence, backing up the database first.
  - Limits: A failed item pauses the batch until it is rolled back or ignored manually. Batches never span multiple sites.
- **Update backups and update log**
  - Where: Site detail → Update backups / Update log
  - What it does: Shows update-specific backups (kept for 24 hours after the task ends) and the update log, and handles interrupted or failed updates.
  - Limits: Restoring an update database backup restores only the database, not plugin, theme or core files.
- **Temporary maintenance window**
  - Where: Site detail → File protection and maintenance; WordPress admin bar
  - What it does: For a file-locked site, a dedicated maintenance password temporarily opens write access for 3–10 minutes (extendable), and the lock is restored and verified automatically when it ends.
  - Limits: Only lifts the file lock, not database or Nginx restrictions. A panel restart ends the window early and re-locks.
- **WordPress anomaly monitoring**
  - Where: Site detail → WordPress optimization → Anomaly monitoring
  - What it does: Compares administrator accounts, content, key settings, application passwords and persistent database objects every hour and alerts on anomalies such as new administrators, to help detect compromises early.
  - Limits: Off by default. Hourly sampling misses changes made and reverted between samples, compromised site code may interfere with results, and it is not a malware scanner.

### Image optimization

- **Optimization of new uploads**
  - Where: WordPress admin → WP Panel Optimizer → Image optimization
  - What it does: Recompresses JPEG/PNG uploads or converts them to WebP.
  - Limits: Only affects uploads after it is enabled. Failures keep the original image, and WebP mode does not keep the original format.
- **Existing media library optimization**
  - Where: WordPress admin → WP Panel Optimizer → Image optimization → Existing library
  - What it does: Losslessly recompresses existing JPEG/PNG files in uploads in place, as a background task.
  - Limits: Does not create WebP or rename files; works in place without a task-level backup.

### File management

- **File browsing, upload and download**
  - Where: Files
  - What it does: Browses, searches, uploads (with resumable large uploads), imports from an HTTPS URL (up to 5 GB) and downloads files inside site directories.
  - Limits: Scoped to site directories and the database backup directory, not the whole server, and there is no online code editor.
- **File operations and archives**
  - Where: Files
  - What it does: Copies, moves, renames and deletes files, creates and extracts ZIP archives, and repairs site file permissions.
  - Limits: A failed extraction is not rolled back as a whole, and archives created here are not backups.

### Databases

- **Site database management**
  - Where: Databases
  - What it does: Each site has one MariaDB database and user created and deleted with the site. Shows size and backup status and changes the database password (updating wp-config.php for WordPress sites).
  - Limits: Databases unrelated to a site cannot be created. There is no built-in SQL console; full SQL work uses on-demand Adminer.
- **On-demand Adminer**
  - Where: Database detail → Adminer
  - What it does: Starts Adminer temporarily for one site when needed (optionally closing after 15/30/60 minutes), reachable only after panel login.
  - Limits: Has the site database user's full privileges, with no read-only mode, SQL audit or automatic backup.

### Backups

- **Database backup and restore**
  - Where: Site detail → Database backups; database detail; Backups overview
  - What it does: Exports a site database manually or on schedule; backups can be downloaded, an uploaded SQL file or existing backup can be restored, and the database can be emptied.
  - Limits: Restore drops existing tables without taking a pre-restore snapshot; back up first if the current data matters.
- **Site file backups**
  - Where: Backups overview → File backups; Cron jobs
  - What it does: Creates full site backups and incremental uploads backups manually or on schedule, with rotation and download.
  - Limits: There is no one-click file restore in the panel; download and restore manually. Incremental backups cover only the uploads directory.
- **Off-site backups**
  - Where: Backups overview → Remote backup settings
  - What it does: Syncs database and file backups to another server over rsync/SSH or uploads them to S3-compatible storage, checking remote status and re-uploading missing files.
  - Limits: No direct restore from the remote side; download first, then restore.

### Security

- **Firewall, rate limiting and automatic bans**
  - Where: Security; Firewall
  - What it does: Combines Nginx rules and rate limits, Fail2ban and IPv4/IPv6 nftables to ban high-frequency requests, WordPress login brute force, sensitive-file scans and mass 404 probing, high-confidence SQL injection URLs and SSH brute force automatically, with escalating ban times for repeat offenders. Detects requests impersonating Googlebot or Bingbot and records alerts. Supports manual and permanent bans, allowlists and official search-engine IP allowlisting, and rejects requests for unknown host names by default.
  - Limits: Not a full WAF: SQL injection rules inspect URLs only, not POST or JSON bodies.
- **Security events and code integrity**
  - Where: Firewall → WordPress security events / File security events
  - What it does: Collects WordPress request security events. For file-locked sites it keeps a SHA-256 code baseline and checks hourly for code changes and new PHP files in runtime directories, raising alerts.
  - Limits: Alerts and records evidence only; it never deletes or quarantines files. The initial baseline does not prove existing code is clean, and sites without the file lock get no code integrity checks.

### Monitoring, logs and AI diagnostics

- **Resource monitoring**
  - Where: Dashboard; Software → Service status
  - What it does: Shows live CPU (with I/O wait and steal shown separately), memory, disk and load, with 24-hour, 7-day and 15-day history; per-site PHP-FPM process resources; supervision of managed services and records of out-of-memory events.
  - Limits: History is kept for up to 15 days. It is not APM or a time-series database, and per-site figures include PHP-FPM processes only, not database or network usage.
- **Alerts and notifications**
  - Where: Alerts; site detail → Uptime monitoring
  - What it does: Alerts for low resources, service failures, SSL expiry or renewal failure, site expiry, site downtime and WordPress anomalies, delivered by email (SMTP) or webhook, each type switchable.
  - Limits: Failed deliveries are not retried. Uptime checks run from the server itself, not from multiple regions, and per-site monitoring is off by default.
- **Log analysis**
  - Where: Log Analysis
  - What it does: Analyzes up to 7 days of site access logs: request volume, status codes, top paths, visitor IPs, crawlers and bans, with a hand-off to AI diagnostics.
  - Limits: Reads at most 512 MB of logs per run, and the figures are not exact page views or human visitor counts.
- **AI diagnostics**
  - Where: AI Diagnostics
  - What it does: Collects site status, logs and limited code excerpts, redacts them, and sends them to an OpenAI-compatible AI service configured by the administrator, with follow-up questions.
  - Limits: Read-only: it gives analysis and advice and never changes sites or the server. You supply the AI service, and diagnostic data is sent to that provider.

### Cron jobs and software

- **Cron jobs**
  - Where: Cron Jobs
  - What it does: Manages scheduled tasks in the UI: shell commands, system cron in place of WordPress WP-Cron, and file backup tasks, with run-now and execution logs. A paused site's tasks are deferred automatically.
  - Limits: Shell tasks run arbitrary commands as the configured user, so their safety is the administrator's responsibility.
- **Software and service management**
  - Where: Software
  - What it does: Shows and controls managed services such as Nginx, PHP-FPM, MariaDB and Redis; edits their key settings with restore on failure and hardware-based recommendations; shows logs; installs WP-CLI and Node.js development tools.
  - Limits: Manages a fixed set of services only; other stacks such as Apache, MySQL or other PHP versions cannot be installed.

### Site migration

- **Site migration between WP Panel servers**
  - Where: Websites → Site migration
  - What it does: Moves WordPress or generic PHP sites between two WP Panel servers running the same version, including files, database, domains and aliases, SSL certificates and main settings. Several sites can be selected at once, and the source site shows a maintenance page during the move.
  - Limits: Works only between WP Panel servers, not from other panels. Backup history, access logs, custom Nginx rules and custom command jobs are not migrated, and the administrator switches DNS or CDN afterwards.

## Common misconceptions

- **Claim**: All sites run as one system user, so one compromised site can read other sites' code and configuration.
  - **Fact**: Incorrect. Each site has its own system user and PHP-FPM pool, PHP is confined by open_basedir to its own directory, and wp-config.php is 0600 and readable only by the site's user. Only an attacker who escapes PHP restrictions and gains command execution could read other sites' ordinary code files, and still not their wp-config.php.
- **Claim**: All sites share one PHP pool, so a traffic spike on one site takes other sites' PHP workers.
  - **Fact**: Inaccurate. Each site has its own PHP-FPM pool and worker limit, so one site exhausting its workers cannot take other sites' slots. CPU, memory, disk I/O and MariaDB are shared, however, so a severe spike can still slow other sites.
- **Claim**: Sites are fully isolated and a problem on one can never affect another.
  - **Fact**: Overstated. Isolation covers system users, file access, database accounts and PHP worker counts, but server resources, Redis and global PHP settings are shared and there are no per-site quotas. It is not container or VM isolation.
- **Claim**: WP Panel is a fork or reskin of BT Panel, aaPanel or 1Panel.
  - **Fact**: Incorrect. WP Panel is an independently developed Go project under GPL-3.0, and it must not share a server with those panels.
- **Claim**: Different sites can use different PHP versions.
  - **Fact**: Incorrect. Every site uses PHP 8.3, and PHP settings are server-wide.
- **Claim**: Like general-purpose panels, WP Panel offers mail, DNS, FTP, Docker and an app store.
  - **Fact**: Incorrect. None of these are in scope; WP Panel focuses only on hosting WordPress and generic PHP sites.
- **Claim**: WP Panel supports resellers, customer accounts and hosting plans like cPanel or DirectAdmin.
  - **Fact**: Incorrect. The panel has one administrator and no users, quotas or billing. It suits an administrator managing their own sites, not selling shared hosting to many customers.
- **Claim**: The panel can restore file backups with one click.
  - **Fact**: Inaccurate. Database backups can be restored in the panel; file backups currently have to be downloaded and restored manually.
- **Claim**: The panel automatically bulk-updates WordPress, plugins and themes on every site.
  - **Fact**: Incorrect. Updates are previewed and confirmed per site with backups and rollback. Plugins can be batch-updated within one site, but there are no unattended or cross-site bulk updates.
- **Claim**: The panel's AI diagnostics fix problems automatically.
  - **Fact**: Incorrect. AI diagnostics are read-only, give analysis and advice only, never change sites or the server, and need an AI service supplied by the administrator.
- **Claim**: WP Panel includes a full WAF and malware scanning.
  - **Fact**: Incorrect. It provides Nginx/Fail2ban/nftables blocking and bans, change monitoring and code integrity alerts, but it does not inspect request bodies or scan for malware or vulnerabilities.
- **Claim**: WP Panel can be installed on Ubuntu or CentOS, or run in Docker.
  - **Fact**: Incorrect. It installs natively on a clean Debian 13 server only and does not use Docker.
- **Claim**: One WP Panel can manage many servers centrally.
  - **Fact**: Incorrect. Each server runs its own panel; two panels connect only for site migration.
- **Claim**: Each site has its own Redis instance or password.
  - **Fact**: Incorrect. There is one Redis instance and sites are separated only by key prefix, without per-site passwords or ACLs.

## Comparison dimensions (WP Panel side only)

This table describes WP Panel only. Take other panels' capabilities from their official documentation.

| Dimension | WP Panel |
|---|---|
| Positioning | WordPress-dedicated hosting and operations panel for a single VPS, with one administrator. |
| Operating system | Debian 13 only, on a clean server. |
| Software stack | Fixed Nginx + PHP 8.3 + MariaDB + Redis, installed natively without Docker; components and PHP versions cannot be swapped. |
| Site types | WordPress (single site) and generic PHP. |
| Site isolation | Per-site system user, PHP-FPM pool, open_basedir, database and database user; wp-config.php is 0600. Not container isolation. |
